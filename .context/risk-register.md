# 风险台账

| 风险 | 触发条件 | 影响 | 缓解策略 |
| --- | --- | --- | --- |
| WhatsApp Web 自动化失效 | WhatsApp Web 页面或 `whatsapp-web.js` 行为变化 | 登录、检测或发送失败 | 保持自动化核心模块隔离，后续可单独适配 |
| 电话号码误解析 | 表格号码格式混乱或国家列缺失 | 发送到错误号码或跳过有效号码 | 使用 `libphonenumber-js`、导入预检、待确认状态 |
| 敏感数据误提交 | Git 跟踪客户号码、登录缓存或报表 | 泄露客户数据或登录状态 | `.gitignore` 排除 `.wwebjs_auth/`、客户表格、进度和报表 |
| 平台限制 | 大批量发送或过快发送 | 账号受限或任务失败 | 保留每日限额、随机间隔、暂停继续，不做风控规避 |
| 本地账号数据被整机复制 | 用户手动复制整机 `userData` 或打包本机数据给别人 | 本地账号记录、任务历史或 WhatsApp 缓存可能被带走 | 发布包不包含 `userData`；账号数据和 WhatsApp 缓存在系统用户目录；同步只通过加密同步包迁移，不迁移 WhatsApp 缓存 |
| 用户误以为新注册会清空旧记录 | 新增认证门禁后未登录无法看到旧工作台数据 | 误判历史丢失，引发数据焦虑 | 启动时迁移 legacy 数据到账号目录且不删除原始数据；`.context` 标记此风险，后续 UI 应继续清晰提示 |
| 第二工作台代理失效 | SOCKS5 断开、账号密码错误、出口 IP 变化或代理服务商轮换 IP | 第二账号可能回落失败或任务中断 | 保存前真实检测，开始任务前复检，运行中 5 分钟巡检；异常时报警并请求任务暂停 |
| 多账号同时自动化风控 | 同机同 IP 或高频运行两个 WhatsApp 账号 | 更容易触发 WhatsApp 风控，CPU/内存占用增加 | 主工作台打开第二工作台前弹风险提示；第二工作台强制代理配置；独立工作台不能继续无限多开 |
| 套餐余额和每日限额混淆 | 用户充值额度当天没用完 | 用户误以为额度清零或软件吞额度 | 价格页明确“未使用额度长期保留”；核心规则区分账户余额、今日已用和每日可用上限 |
| 主工作台重复打开工作台 | 用户连续点击主工作台打开另一个账号 | CPU/内存失控、多个账号并发触发风控 | 主进程按套餐限制独立工作台数量；按钮达到上限时禁用；商业版默认 5 个且不承诺无限 |
| 本地套餐状态与真实支付未接入 | 用户看到套餐页但没有线上订单系统 | 误解为已经有自动充值/账单能力 | 用量、账单、积分页标注当前为规则/占位；后续再接充值账本、支付回调和扣费流水 |
